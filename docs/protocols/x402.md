# x402

The x402 provider supports v2 `exact` on EVM through EIP-3009
`transferWithAuthorization` or, per option, Permit2, on Solana and on NEAR.
Both EVM methods are supported on built-in EVM networks, with settlement
demonstrated on Base Sepolia and Base. Solana has settled on devnet and
mainnet. NEAR remains partial: testnet and mainnet payments used the test
suite's SDK facilitator, with no hosted-facilitator settlement demonstrated.
EVM requirements name the method in `extra.assetTransferMethod`; EIP-3009
also includes the token's EIP-712 domain name and version.

Verification checks the scheme, signature, recipient, amount, validity window,
payer balance, network and asset. Local refusals use x402 error codes where
available, such as `invalid_network`. The provider derives a replay key from
the authorization, which the pipeline reserves before settlement. A successful
settlement records the transaction hash, or the signature on Solana. A success
that names another network, or no transaction in its family's form, unlocks
nothing and leaves the payment's outcome unknown.

A Permit2 proof must name the x402 exact Permit2 proxy as spender and match
the offer's token, amount and `payTo` witness recipient. The gateway checks
these before the facilitator checks the signature, deadline, balance and
Permit2 allowance. Other spenders could redirect funds and are refused as
`invalid_permit2_spender`. A proof using the wrong method or both
authorizations is `unsupported_scheme`: the SDK facilitator chooses Permit2
whenever that authorization is present. Since an owner's Permit2 nonce spans
all tokens, the replay key uses the chain id, Permit2 address, owner and nonce.

On Solana, the buyer signs a token transfer with the facilitator's fee payer,
named in `extra.feePayer` from `/supported`. The facilitator checks the fee
payer, signatures, instruction layout, mint, recipient token account and
amount, then simulates the transaction. The gateway matches the echoed offer's
addresses case-sensitively. Its replay key uses the network and SHA-256 of the
transaction message, excluding signatures, so changing signature bytes,
including the fee payer's, still collides. Unconfirmed broadcasts, duplicate
settlements in flight, and confirmed transactions whose transfers are not yet
visible leave the outcome unknown. The payer recorded is the one verification
reported: the Solana scheme's settlement example names the fee payer as `payer`,
where x402 v2 defines the payer's wallet.

On NEAR, the buyer signs a NEP-366 delegate containing one `ft_transfer` of
the offered amount to `payTo`, with one attached yoctoNEAR. The facilitator's
relayer submits it and pays gas. NEAR adds no scheme-specific `extra`; an
`upfront` offer still carries `extra.paymentFlow`. Before calling
the facilitator, the gateway rejects mismatched tokens, recipients, amounts,
methods or deposits, extra actions, and non-canonical base64 Borsh. The
facilitator checks the signature, full-access key, nonce, delegate block
window and chain state. The replay key uses the network, sender, public key
including its curve, and nonce. Different delegate bytes under the same key
and nonce still collide. The signature names no chain: network binding relies
on the offer and facilitator's RPC. Settlement requires a successful inner
`ft_transfer` receipt. `settlement_failed` without a hash leaves the outcome
unknown because submission may have preceded the SDK exception; with a hash,
it reports a failed inner transfer. Chain-read failures also leave no verdict.
The NEAR specification leaves failure reasons to the facilitator, with an
empty `transaction` even after a submission, so any other failure is a
rejection only when its reason is one the SDK returns before submitting:
`invalid_exact_near_*`, `insufficient_funds` or a version, scheme or network
refusal. Any other reason leaves the outcome unknown.

The signature covers neither the flow nor the resource, so the proof's
`accepted` must match the offer: amount, asset, `payTo` (case-insensitive on
EVM, case-sensitive on Solana and NEAR), and every `extra` key the gateway
sent. An absent `extra.paymentFlow` means `authorization`. A proof's `resource.url`
must equal the challenge's when present. A mismatch is `invalid_payment_requirements`,
refused before the facilitator is called. `maxTimeoutSeconds` and `extra` keys
added by the client are not compared. The facilitator receives the payload
without `resource`, since its `resource://` URL is the gateway's own identifier,
and without `extensions`: the gateway advertises none, and the SDK facilitator
would act on a Permit2 gas-sponsoring extension.

With [several options](../configuration.md#several-options), the challenge uses
`resource://agent-commerce/resources/<id>`. The comparison above selects the
proof's offer; zero or multiple matches yield `invalid_payment_requirements`.
A resource with [its own offers](../configuration.md#a-resources-own-offers)
accepts only proofs matching that list; resources may share offers.

x402 v1 is not accepted. A payload declaring an `x402Version` other than 2 is
refused as `invalid_x402_version` on every carrier. A request carrying only the
v1 `X-PAYMENT` header gets the 402 challenge with
`error: "invalid_x402_version"` in `PAYMENT-REQUIRED`.

`payments.x402.paymentFlow` chooses when an x402 payment settles, and
`payments.mpp.paymentFlow` does the same for MPP. A resource's `paymentFlow`
overrides the setting of whichever rail serves it:

| Flow                           | Order                                 | Backend fails                                          | Settlement refused after backend |
| ------------------------------ | ------------------------------------- | ------------------------------------------------------ | -------------------------------- |
| `authorization` (x402 default) | verify, reserve, call backend, settle | no settlement; attempt recorded as rejected            | response withheld; 402           |
| `upfront` (MPP default)        | verify, reserve, settle, call backend | payment stays settled; receipt records failed delivery | not applicable                   |

The gateway omits `extra.paymentFlow` for the `authorization` flow.
It sets `extra.paymentFlow: "upfront"` for the other flow, as required by
[x402 v2](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md#61-asset-transfer-methods-and-payment-flow-models).
The gateway verifies the proof before calling the backend in either flow.
For `upfront`, it adds a read-only check before the x402 v2
`settle → resource` sequence. Under `authorization`, the backend may finish
work before settlement. A refusal leaves that work unpaid; an uncertain
settlement leaves its payment status unknown. In both cases, the gateway
withholds the backend response. Use `upfront` when backend side effects must
follow payment. Backend time counts toward `maxTimeoutSeconds`: the payment
authorization must remain valid at settlement.

After a rejected x402 attempt, from a backend failure under `authorization` or
a refused settlement, the client can retry the unspent payload and reclaim the
attempt; it still settles at most once, because the chain spends its nonce
once. MPP credentials are single-use per challenge, so a retry returns 402
`PAYMENT_REPLAYED` with a fresh challenge.

Unsupported: the Permit2 gas-sponsoring extensions
(`eip2612GasSponsoring`, `erc20ApprovalGasSponsoring`), the `upto`,
`batch-settlement` and `auth-capture` schemes, multi-asset routing and
dynamic pricing.

Facilitator authentication supports `none`, `bearer` and `cdp`; config rejects
other types. Local mode requires Anvil on `eip155:31337`; all public networks
require remote mode. Mainnet also requires the guardrails in
[configuration.md](../configuration.md#mainnet-guardrails).

## Support matrix

Local settlement runs in the offline E2E suite against real contracts.
Public-network runs come from the [smoke tests](../smoke-tests.md), and the
README lists their transactions.

| Route                                                                      | Support   | Local settlement                                   | Public testnet                            | Mainnet                                   | Limits                                                                                                                                  |
| -------------------------------------------------------------------------- | --------- | -------------------------------------------------- | ----------------------------------------- | ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| EIP-3009 on Base Sepolia and Base                                          | supported | Anvil                                              | Base Sepolia, x402.org                    | Base, PayAI                               |                                                                                                                                         |
| EIP-3009 on Ethereum, Polygon, Arbitrum One and Sepolia, Avalanche C-Chain | supported | two custom-id Anvil chains, remote facilitator     | not run                                   | not run                                   | needs a facilitator that lists the network; PayAI did not list Ethereum on 2026-10-10                                                   |
| Permit2 on the built-in EVM networks                                       | supported | Anvil with the deployed Permit2 and proxy bytecode | Base Sepolia, x402.org                    | Base, PayAI                               | the buyer approves Permit2 once, paying gas; no gas-sponsoring extensions                                                               |
| EVM networks declared in config                                            | partial   | custom-id Anvil chains                             |                                           |                                           | the operator supplies the chain and all four asset fields                                                                               |
| Solana                                                                     | supported | `solana-test-validator`, SDK facilitator           | devnet, x402.org                          | mainnet, PayAI                            | the merchant's token account must exist; a signed transfer expires with its blockhash                                                   |
| NEAR                                                                       | partial   | NEAR sandbox, SDK facilitator                      | testnet, SDK facilitator run by the suite | mainnet, SDK facilitator run by the suite | not run through a hosted facilitator; FastNEAR's requires an API key. The merchant needs a storage deposit, the buyer a full-access key |

Every public-network x402 payment was signed by the x402 SDK's own client for
its family. Other wallets and clients have not been tested.
